# DAG 화면 디자인 인풋 정리 (스켈레톤 작성용)

Claude 디자인으로 스켈레톤을 만들기 전, 확인된 화면 구성 요소와 기존 명세
(`simulation-supply-chain-tool.md`, `ARCHITECTURE.md`, `frontend/docs/FRONTEND_ARCHITECTURE.md`,
`frontend/docs/DAG_VISUALIZATION.md`)를 대조해서 **디자인에서 빠지면 안 되는 인풋/아웃풋**을 정리한다.

## 0. 먼저 확인해야 하는 구조적 차이

확인된 구성은 **한 화면**에 다음 세 가지를 동시에 보여준다: Impact DAG + 대응안 후보 랭킹 + SOP 자동
매칭. 그런데 `FRONTEND_ARCHITECTURE.md` §3 라우팅 표는 이 세 가지를 **별도 라우트**(`/incidents/:id/dag`,
`/incidents/:id/candidates`, `/incidents/:id/sop`)로 분리해뒀다.

→ 이 구성이 맞다면 이건 "탭으로 나뉜 화면"이 아니라 **사건 대응용 단일 대시보드("작전실" 뷰)**를
지향하는 것으로 보인다. 스켈레톤을 그리기 전에 다음을 확정해야 한다:

- [ ] 이 레이아웃을 메인 화면으로 하고, 기존 라우팅 표의 개별 페이지들은 이 화면의 서브 상세뷰(모달/드릴다운)로 재배치할지
- [ ] 아니면 이 화면 자체가 새 라우트(예: `/incidents/:id`의 기본 랜딩)이고, DAG/candidates/SOP 개별 라우트는 그대로 유지하되 이 화면이 "요약 통합 뷰"로 추가되는 것인지

이 결정에 따라 스켈레톤의 전체 골격(탭 구조 유무)이 달라지므로, 디자인 착수 전 다른 세션과 맞춰야
한다.

## 3. Impact DAG 캔버스 (좌측 메인 영역)

`frontend/docs/DAG_VISUALIZATION.md`에서 이미 스키마 초안을 잡아뒀지만, 확인된 구성을 보면 **엔티티 타입
분류가 기존 초안과 다르다** — 반영 필요.

- 기존 초안(`DAG_VISUALIZATION.md`): `nodeType: "trigger" | "impact" | "outcome"` (시각 스타일용 3분류)
- 확인된 실제 노드 타입: **항만 / 부품 / 생산라인 / 운송 / 딜러** — 도메인 엔티티 종류를 그대로 라벨링

→ `nodeType`을 스타일용 분류와 도메인 엔티티 분류 두 개로 분리해야 한다. 예:

```ts
type ImpactDagNode = {
  // ...기존 필드(DAG_VISUALIZATION.md §2.2)...
  entityType: "port" | "part" | "production_line" | "transport" | "dealer"; // 신규 — 확인된 구성 기준
  delayDays?: number;      // "+1.5일 지연"
  costImpact?: number;     // "996.1억원" — 통화 단위/포맷 확정 필요(억원 고정 표기인지)
};
```

확인된 노드/엣지 표현 규칙(디자인에 그대로 반영 권장):

- 노드 박스 상단에 작은 회색 텍스트로 엔티티 타입, 그 아래 굵은 글씨로 이름
- 노드 우측 상단에 작은 점(dot) — 상태/심각도 표시로 추정. `DAG_VISUALIZATION.md`의 `uncertainty`
  필드와 매핑되는지, 아니면 별도 "미해결/확인필요" 플래그인지 확인 필요
- 영향받은 하위 노드는 지연일수 + 비용을 한 줄로 병기 ("+1.5일 지연ㆍ996.1억원") — 루트 노드(트리거,
  예: "부산신항 HPNT")는 지표 없이 이름만 표시
- 엣지는 점선(dashed) — `DAG_VISUALIZATION.md` §2.3에서 제안한 "INFERENCE=파선" 규칙과 일치. 다만
  확인된 구성에서는 FACT/INFERENCE 구분 없이 전부 점선으로 보여서, 근거 타입별 실선/파선 구분을 실제로
  적용할지 재확인 필요
- 레이아웃은 좌→우 계층형(트리거 → 부품 2종 병렬 → 생산라인 2종 병렬 → 운송 → 항만 하역 → 딜러 3개
  권역 fan-out) — `DAG_VISUALIZATION.md` §2.1에서 권장한 `dagre` 좌→우(LR) 배치와 일치, 그대로 진행

**확인된 구성에는 없지만 명세상 필요한 것 (디자인에서 자리를 비워둬야 함)**:
- 노드 클릭 시 근거·불확실성 패널 (`FRONTEND_ARCHITECTURE.md` §3, `ARCHITECTURE.md` §7.1 요구사항) —
  클릭 인터랙션 결과는 확인되지 않음. 스켈레톤에 "노드 클릭 → 사이드/모달 패널" 자리를 반드시 포함해야 함
- FACT/INFERENCE/ASSUMPTION 뱃지 — 노드/근거 어디에도 명시적으로 안 보임. 디자인 누락 위험 높은 항목

## 4. 대응안 후보 랭킹 패널 (우측 상단)

확인된 필드 초안:

```ts
type ResponseCandidateRow = {
  rank: number;                 // 1~4
  name: string;                 // "안전재고 사전 당김"
  savingsAmount: number;        // -535.6억원 (절감액, 음수=손실감소)
  description: string;          // "생산라인 안전재고를 선제 확보해 지연 흡수분 확대"
  remainingLoss: number;        // 잔여손실 564.6억원
  mitigationRatio: number;      // progress bar 값 — 잔여손실 / 기준손실 비율로 추정, 계산식 확인 필요
};
```

**주의**: 랭킹 순서대로 잔여손실이 564.6억 → 1011.7억 → 1100.2억으로 **증가**한다. 이게 "1번이 가장
효과적인 단독 대응안이고 뒤로 갈수록 덜 효과적"이라는 의미인지(각 후보를 독립적으로 적용했을 때의 결과),
아니면 순차 누적 적용 결과인지 확인된 정보만으로는 확정할 수 없음 — **백엔드 세션에 계산 의미 확인
필요**. 이 해석에 따라 progress bar가 "개별 후보의 손실 완화율"인지 "누적 완화율"인지가 달라진다.

**확인된 구성에는 없지만 명세상 필요한 것**:
- 기대손실 P90·CVaR (`simulation-supply-chain-tool.md` §5.1) — 랭킹 카드에는 단일 절감액/잔여손실만
  보이고 분포(P90/CVaR)는 안 보임. 별도 차트 영역(Recharts, 기존 `candidates` 라우트 몫)이 필요한지,
  이 화면에도 압축해서 넣을지 결정 필요
- 지금 대응 / 6시간 후 대응 / 무대응 baseline 비교 — 확인되지 않음
- 핵심 민감도 변수 — 확인되지 않음
- 신뢰도·불확실성 범위 — 확인되지 않음
- 결정기한 카운트다운 (`simulation-supply-chain-tool.md` §5.1 "권고 결정기한") — 헤더의 "진입 N5ㆍ2일"이
  이 역할을 겸하는 건지, 별도 카운트다운 UI가 필요한지 확인 필요
- 승인/조건부승인/반려/수정요청 액션 버튼 (`ARCHITECTURE.md` §7.1 "담당자 승인" 단계) — 확인되지 않음.
  이 화면에서 바로 승인까지 하는 화면인지, 승인은 별도 화면(`/incidents/:id/approval`)인지 확정 필요

type ExcludedCandidate = {

## 6. SOP 자동 매칭 패널 (우측 하단)

```ts
type MatchedSop = {
  code: string;              // "SOP-LINE-01"
  title: string;             // "생산라인 정지 위험 대응 (JIT 부품 결품)"
  owningTeam: string;        // "공장 운영팀"
  steps: string[];           // 번호 매겨진 절차 목록
  reference: string;         // "생산 비상대응 매뉴얼 §3.2ㆍ부품 안전재고 기준표"
  expandedByDefault: boolean; // 첫 번째 항목만 펼침, 나머지는 접힘
};
```

- 헤더에 매칭 건수 표시 ("6건 매칭")
- 안내 문구 "상황 분석 결과에 맞는 대응 절차를 자동으로 찾아줍니다" + "※ 데모용 예시 SOP" 워터마크성
  문구 — 데모/시드 데이터임을 명시하는 표기는 실제 배포판에서도 유지할지 결정 필요
- `simulation-supply-chain-tool.md` §6.2 "역할별 SOP 미리보기"와 대응. 다만 §6.2는 **승인 이후** 담당자별
  발송 대상 SOP인데, 이 화면은 **승인 전 참고용**으로 자동 매칭해서 보여주는 것으로 보임 — 같은 SOP
  데이터를 승인 전(참고)과 승인 후(배포) 두 시점에 다른 목적으로 재사용하는 구조인지 확인 필요

## 7. 인터랙션 → API 매핑 정리

| 인터랙션 | 매핑되는 API(추정) |
|---|---|
| "다시 실행" 클릭 | `POST /incidents/{id}/simulate` |
| DAG 노드 클릭 | (신규 정의 필요) 근거/불확실성 패널 오픈 — 별도 API 없이 이미 받은 DAG 응답의 필드로 렌더링 가능할 것으로 추정 |
| SOP 아코디언 펼침/접힘 | 클라이언트 로컬 상태, API 호출 없음 |
| 대응안 후보 카드 클릭(있다면) | 클릭 결과는 확인되지 않음 — 상세 비교 화면(`/incidents/:id/candidates`)으로 이동인지, 이 화면 내 확장인지 확인 필요 |
| 자유 텍스트 인풋 제출 | 사건 원문 수정 후 재해석 트리거인지, 읽기 전용 표시인지 확인 필요(이미 값이 채워진 상태만 확인됨) |

## 8. 상태(로딩/에러/빈 값) — 별도 설계 필요

확인된 구성은 데이터가 이미 다 채워진 "정상" 상태 1컷뿐이다. 스켈레톤 단계에서 최소한 아래는 자리를
잡아둬야 함:

- DAG/후보/SOP 각각의 로딩 스켈레톤
- `POST /simulate` 재실행 중 로딩 상태 ("다시 실행" 버튼 자체의 로딩 표시)
- SSE `dag_updated` 등으로 갱신될 때의 강조 표시 (새 노드/변경된 수치를 어떻게 시각적으로 알릴지) —
  `frontend/docs/DAG_VISUALIZATION.md` §2.5 참고
- 매칭 SOP 0건일 때, 대응안 후보 0건일 때의 빈 상태
- "AI: 캐시 폴백" 외의 다른 AI 상태(정상/오류)일 때의 표시 차이
