# 제약 검증 에이전트 (constraint-validation)

## 정체성

"이론적으로 가능한 것"과 "실제로 지금 할 수 있는 것"을 구분하는 역할이다. 이 페르소나는 회의적이다 — 후보가 그럴듯해 보여도 운송수단·항만 슬롯·예산·계약 조건 중 하나라도 막히면 통과시키지 않는다. 다만 무조건 탈락시키지 않고, 조건부로 가능한 경우 필요한 선행조치를 함께 표시한다.

## 담당 범위

- **API**: 별도 화면 API 없음 — `POST /incidents/{id}/simulate` 파이프라인의 2단계로 내부 실행됨. 결과는 `GET /incidents/{id}/candidates`로 조회됨(제외 사유 포함)
- **DB 테이블**: `response_candidates` (실행 가능성·제약 검증 결과 필드를 갱신)
- **코드 위치(예정)**: `backend/app/services/simulate/constraint_validation.py`

## 입력 / 출력

- **입력**: 대응 설계 에이전트가 만든 후보 목록, 운영 스냅샷(자원 가용량), 계약/통관/법무 조건(RAG)
- **출력**: 실행 가능/조건부 가능/불가능으로 분류된 후보 목록 + 제외 사유 또는 선행조건 → 시뮬레이션 에이전트([simulation.md](./simulation.md))는 실행 가능/조건부 후보만 받는다

## 핵심 설계 원칙

- 검증 항목(업무 명세 §4.3): 운송수단/항만 슬롯/작업자/설비 용량, 착수 가능시각과 완료기한, 예산과 비용 승인 한도, 계약·통관·품질·법무 조건, 다른 사건/대응안과의 자원 중복, 담당 조직의 실행 권한과 운영시간.
- **실행 불가능한 후보는 반드시 제외 사유를 기록한다** — 근거 없이 조용히 빼지 않는다. 이 사유는 나중에 프론트 "대응안 비교 카드"의 제외 사유 표시(`ARCHITECTURE.md` §7.1)에 그대로 노출된다.
- 조건부 가능 후보는 선행조치와 조건을 함께 표시한다 (단순 이진 판정이 아니다).
- 자원 중복 검증은 이 사건 하나만 보지 않는다 — 동시에 진행 중인 다른 사건/대응안의 자원 점유도 함께 확인해야 한다.

## 의존 관계

- **선행**: 대응 설계 에이전트
- **후행**: 시뮬레이션 에이전트 (통과한 후보만 시뮬레이션 대상이 됨)
- **순차 필수**: 대응안 후보 → 제약 검증 → 시뮬레이션 (업무 명세 §7.3)

## 작업 지침 (구현 체크리스트)

1. `response_candidates`에 검증 상태(가능/조건부/불가능), 제외 사유, 선행조건 필드를 추가한다.
2. 자원 중복 검증은 사건 단위가 아니라 전역(활성 사건 전체) 자원 점유 뷰를 참조하도록 설계한다.
3. baseline(무대응) 후보는 제약 검증을 통과시키는 특수 케이스로 처리한다 — 무대응은 항상 "실행 가능"하다.
4. 제외 사유는 자유 텍스트가 아니라 카테고리(자원 부족/기한 불가/예산 초과/계약 위반 등) + 상세 설명 구조로 저장해 프론트에서 필터링 가능하게 한다.

## 완료 기준 (Definition of Done)

- [ ] 자원이 부족한 후보가 제외 사유와 함께 걸러짐
- [ ] 조건부 가능 후보에 선행조건이 표시됨
- [ ] baseline은 항상 실행 가능으로 처리됨
- [ ] 테스트 최소 3케이스: (1) 정상 통과 (2) 자원 부족으로 제외 + 사유 확인 (3) 조건부 가능 판정 + 선행조건 확인
