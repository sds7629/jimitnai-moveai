# 지식 검색 에이전트 (knowledge-retrieval)

## 정체성

과거 사고, SOP, 계약, 플레이북을 뒤져 "지금 이 상황과 비슷한 사례에서는 어떻게 했는가"를 찾아오는 역할이다. 이 페르소나는 검색 결과를 그대로 믿지 않는다 — 문서 유형에 따라 유효기간이 지난 계약/SOP를 걸러내고, 문서 유형별로 다른 청킹 단위를 존중해야 원래 맥락이 깨지지 않는다는 것을 안다.

## 담당 범위

- **API**: 사용자 화면용 API는 없음 (`ARCHITECTURE.md` §7.1: "화면 없이 백엔드 시드 스크립트로만 처리"). 내부적으로 시뮬레이션 에이전트가 호출하는 검색 함수를 소유한다.
- **DB 테이블**: `documents`, `document_chunks` (pgvector 임베딩 컬럼 포함)
- **코드 위치(예정)**: `backend/app/rag/` (임베딩·청킹·검색), `backend/app/scripts/seed_documents.py`

## 입력 / 출력

- **입력**: (검색 시점) Impact DAG 경로 요약 또는 사건 유형 키워드, `doc_type` 필터 조건
- **출력**: top-k 검색 결과 (문서 유형별 병합) → 시뮬레이션 에이전트([simulation.md](./simulation.md))의 LLM 프롬프트에 삽입

## 핵심 설계 원칙

- 문서 유형별 청킹 전략을 다르게 적용한다 (§3): 계약=조항 단위, SOP=절차 단위, 과거 사고=사건 단위(원인→대응→결과를 한 청크로), 플레이북=대응 패턴 단위. 하나의 범용 청커로 통일하지 않는다.
- 임베딩은 Gemini Embedding API를 사용하고, 기존 `llm/` 프로바이더 추상화의 인증 체계를 그대로 공유한다 (별도 API 키 관리 체계를 새로 만들지 않는다).
- 검색은 pgvector cosine similarity + `doc_type` 필터 + 유효기간 필터(계약/SOP는 최신 유효본만)를 함께 적용한다. 유사도만으로 정렬해 만료된 계약 조항을 근거로 쓰는 것을 방지한다.
- 시드 문서 적재는 화면이 아니라 스크립트로만 한다 — RAG 업로드 UI는 이번 스코프에 없다.

## 의존 관계

- **선행**: 없음 (문서는 사전 적재됨, 시드 스크립트로 독립적으로 준비 가능)
- **후행**: 시뮬레이션 에이전트가 LLM 프롬프트 구성 시 이 검색 결과를 사용
- **병렬 가능**: 데이터 수집 구간에서 운영 그래프 에이전트의 스냅샷 조회와 병렬로 실행 가능 (업무 명세 §7.2 "사건 분석" 구간)

## 작업 지침 (구현 체크리스트)

1. `documents`/`document_chunks` 스키마를 문서 유형(`doc_type`)과 유효기간(계약/SOP의 `valid_from`/`valid_until`) 필드를 포함해 확정한다.
2. 문서 유형별 청킹 함수를 4종(계약/SOP/사고/플레이북)으로 분리해 구현한다 — 단일 청킹 함수에 if분기로 몰아넣지 않는다.
3. Gemini Embedding API 클라이언트를 `llm/` 프로바이더 추상화 아래에 둔다 (`feature/llm-provider` 브랜치와의 병합 지점 확인).
4. 검색 함수는 `doc_type` 리스트 + top-k + 유효기간 필터를 파라미터로 받도록 설계한다.
5. 시드 시나리오 3종(적체/파업/관세)에 대응하는 최소 문서 샘플(과거 사고 1건, SOP 1건, 플레이북 1건 이상)을 먼저 적재해 검색 파이프라인을 검증한다.

## 완료 기준 (Definition of Done)

- [ ] 문서 유형별 청킹이 각기 다른 단위로 저장됨을 확인
- [ ] `doc_type` + 유효기간 필터가 적용된 검색이 만료 문서를 제외함을 확인
- [ ] 시드 시나리오 3종 각각에 대해 관련 문서가 top-k에 포함됨을 확인
- [ ] 테스트 최소 3케이스: (1) 정상 검색 결과 반환 (2) 유효기간 만료 문서 제외 (3) 존재하지 않는 `doc_type` 조회 시 빈 결과 처리
