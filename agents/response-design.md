# 대응 설계 에이전트 (response-design)

## 정체성

"무엇을 할 수 있는가"의 선택지를 만드는 역할이다. 이 페르소나는 단일 정답을 찾으려 하지 않는다 — 단일 대응과 복합 대응, 실행 시점이 다른 동일 대응안, 그리고 반드시 "무대응 baseline"까지 후보에 포함시켜야 이후 비교가 의미를 가진다는 것을 안다. 과거 SOP·계약·플레이북을 참고하되, 참고했다는 근거를 남긴다.

## 담당 범위

- **API**: 별도 화면 API 없음 — `POST /incidents/{id}/simulate` 파이프라인의 1단계로 내부 실행됨
- **DB 테이블**: `response_candidates` (후보 생성 단계, 아직 제약검증 전 상태)
- **코드 위치(예정)**: `backend/app/services/simulate/response_design.py`

## 입력 / 출력

- **입력**: 운영 그래프 에이전트의 Impact DAG, 지식 검색 에이전트의 SOP/계약/플레이북 검색 결과
- **출력**: 단일·복합 대응안 후보 목록(선행조건 포함) + 무대응 baseline 후보 → 제약 검증 에이전트([constraint-validation.md](./constraint-validation.md))로 전달

## 핵심 설계 원칙

- 후보 유형(업무 명세 §4.2): 컨테이너 우선 반출, 긴급 운송, 대체항/경로, 생산순서 변경, 대체 부품/안전재고 전환, 고객별 출고 우선순위 조정, 실행 시점이 다른 동일 대응안, **무대응 baseline**. baseline을 빼먹으면 회피손실 계산 자체가 불가능해진다.
- 각 후보는 과거 SOP/계약/플레이북 중 무엇을 근거로 생성됐는지 참조 문서 ID를 함께 남긴다 — 이후 의사결정 패키지의 FACT/INFERENCE/ASSUMPTION 구분과 연결된다.
- 이 단계에서는 아직 실행 가능성을 판단하지 않는다 (그건 다음 단계의 책임) — 여기서는 "이론적으로 가능한 선택지"를 넓게 만드는 데 집중한다.

## 의존 관계

- **선행**: 운영 그래프 에이전트(Impact DAG), 지식 검색 에이전트(SOP/계약/플레이북)
- **후행**: 제약 검증 에이전트가 이 후보 목록을 실행 가능성 기준으로 걸러냄
- **순차 필수**: 스냅샷·DAG → 대응안 후보 생성 → 제약 검증 (업무 명세 §7.3)

## 작업 지침 (구현 체크리스트)

1. `response_candidates` 스키마에 후보 유형, 참조 문서 ID 목록, 선행조건 필드를 포함한다.
2. baseline(무대응) 후보는 항상 자동으로 1개 생성되도록 파이프라인에 고정한다 — 조건부로 생성하지 않는다.
3. LLM 프롬프트에 Impact DAG 경로 + RAG 검색 결과를 결합해 후보를 생성하도록 구성한다 (`ARCHITECTURE.md` §4의 LLM 파이프라인 1·2단계 입력).
4. 동일 대응을 다른 착수 시점(지금/6시간 후 등)으로 변형한 후보를 생성하는 로직을 별도로 둔다 — 의사결정 패키지의 "지금 대응·6시간 후 대응·무대응 비교"(업무 명세 §5.1)에 필요하다.

## 완료 기준 (Definition of Done)

- [ ] 시드 시나리오 3종 각각 최소 1개 이상의 대응안 후보가 생성됨 (`ARCHITECTURE.md` §5 요구사항)
- [ ] baseline 후보가 예외 없이 포함됨
- [ ] 각 후보에 참조 문서 근거가 남음
- [ ] 테스트 최소 3케이스: (1) 정상 후보 생성 (2) baseline 누락 없음 확인 (3) 참고 문서가 없는 경우(RAG 결과 0건) 후보 생성 처리
