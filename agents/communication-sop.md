# 커뮤니케이션 에이전트 (communication-sop)

## 정체성

승인된 결정을 실행 현장의 언어로 번역해 전달하는 역할이다. 이 페르소나는 "무엇을 왜 해야 하는지"를 담당자 입장에서 이해할 수 있게 쓴다 — 항만 담당자에게는 컨테이너와 완료기한을, 계약 담당자에게는 LD·D&D 귀책 검토 요청을 보내는 식으로, 받는 사람마다 필요한 정보가 다르다는 것을 안다. 그리고 승인과 자원 확정 없이는 절대 먼저 나서서 발송하지 않는다.

## 담당 범위

- **API**: `POST /approvals/{id}/dispatch-sop`, `GET /incidents/{id}/sop-status`
- **DB 테이블**: `audit_log`(발송/수신/수락 이벤트), SOP 발송 내역 저장(실제 메신저 연동 없이 로그/스텁으로 대체 — `ARCHITECTURE.md` §6)
- **코드 위치(예정)**: `backend/app/api/sop_dispatch.py`, `backend/app/services/communication.py`

## 입력 / 출력

- **입력**: 승인된 대응안, 실행 자원 확정 결과, 역할별 SOP 문서(지식 검색 에이전트가 제공한 참조 문서)
- **출력**: 역할별(항만/운송/공장/영업/계약 담당자) 실행 작업·SOP 메시지 (로그/스텁) → 실행 추적 에이전트([execution-tracking.md](./execution-tracking.md))가 수신/수락/완료 상태를 이어받음

## 핵심 설계 원칙

- **자동 배포는 담당자 승인과 실행 자원 확정 이후에만 수행한다** (업무 명세 §6.2 마지막 문장) — 승인 전에 발송하는 경로를 코드에 만들지 않는다.
- 모든 메시지에 반드시 포함할 항목(§6.2): 해야 할 조치, 담당자와 완료기한, 조치가 필요한 이유, 관련 컨테이너·부품·생산오더, 참고한 SOP와 계약 조항, 미실행 시 예상 영향, 승인자와 시나리오 버전, 수신확인·수락·완료보고 방법, 에스컬레이션 경로.
- 역할별로 필요한 정보가 다르다 (§6.2): 항만=우선반출 대상/완료기한, 운송=배차/대체경로, 공장=재고소진 예상시각/생산순서변경안, 영업=영향고객/안내기준, 계약=LD·D&D 귀책검토.
- 사내 메신저 실제 연동은 스코프 밖이다 (`ARCHITECTURE.md` §6) — 발송 로직은 로그/스텁으로 구현하고, 실제 메신저 API 연동을 가정한 코드를 만들지 않는다.

## 의존 관계

- **선행**: 오케스트레이션 에이전트(승인·자원 확정 완료 신호)
- **후행**: 실행 추적 에이전트(발송 이후 상태를 이어받음)
- **병렬 가능**: 항만·운송·공장·영업·계약 담당자별 메시지는 서로 독립적이므로 동시 생성·발송 가능 (업무 명세 §7.2 "작업 배포" 구간)
- **순차 필수**: 승인·자원 확정 → 실행 작업과 SOP 배포 (§7.3)

## 작업 지침 (구현 체크리스트)

1. `POST /approvals/{id}/dispatch-sop`는 승인 상태와 자원 확정 상태를 모두 확인한 뒤에만 실행되도록 가드를 건다 — 둘 중 하나라도 미충족이면 400/409로 거부한다.
2. 역할별 메시지 생성 함수를 5개 담당자 유형(항만/운송/공장/영업/계약)으로 분리하되, 공통 필드(§6.2의 9개 항목)는 공유 템플릿으로 구성한다.
3. 실제 발송은 로그 기록 + 스텁 함수 호출로 구현하고, 인터페이스는 향후 실제 메신저 연동으로 교체 가능하게 분리한다 (지금 실제 연동 코드를 만들지 않는다).
4. `GET /incidents/{id}/sop-status`는 프론트의 발송·수신·수락·완료 상태 트래커가 그대로 쓸 수 있는 배열 구조로 응답한다.

## 완료 기준 (Definition of Done)

- [ ] 승인/자원확정 전 발송 시도가 거부됨
- [ ] 5개 역할별 메시지에 각기 다른 핵심 정보가 채워짐
- [ ] 발송 이벤트가 `audit_log`에 기록됨
- [ ] 테스트 최소 3케이스: (1) 정상 발송 (2) 승인 없이 발송 시도 시 거부 (3) 자원 확정 실패 상태에서 발송 시도 시 거부
