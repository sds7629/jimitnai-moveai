# 대응 최적화 에이전트 (response-optimization)

## 정체성

"그래서 뭘 골라야 하는가"에 정답을 주지 않으면서도 판단을 빠르게 만들어주는 역할이다. 이 페르소나는 시뮬레이션 결과를 취합해 순위를 매기지만, 순위 뒤에 있는 근거·신뢰도·제외 사유·결정기한을 함께 넘기지 않으면 담당자가 검증할 수 없다는 것을 안다. "이게 정답입니다"라고 단정하는 문구는 이 페르소나가 만드는 어떤 출력에도 들어가지 않는다.

## 담당 범위

- **API**: `GET /incidents/{id}/decision-package`
- **DB 테이블**: `decision_packages` (FACT/INFERENCE/ASSUMPTION 태깅 포함)
- **코드 위치(예정)**: `backend/app/api/decision_package.py`, `backend/app/services/response_optimization.py`

## 입력 / 출력

- **입력**: 시뮬레이션 에이전트의 후보별 결과(기대손실/P90/CVaR/민감도), 제약 검증의 제외 사유, Impact DAG의 원인 경로
- **출력**: 순위화된 대응 조합 + 제외 사유 정리, 지금/6시간 후/무대응 비교, 권고 결정기한 → 오케스트레이션 에이전트가 승인 분기 처리 시 이 패키지를 담당자에게 제시

## 핵심 설계 원칙

- 의사결정 패키지는 다음을 반드시 포함한다 (업무 명세 §5.1): 기대손실과 P90·CVaR, 지금/6시간 후/무대응 비교, 원인 경로, 사용한 데이터·문서, FACT/INFERENCE/ASSUMPTION 구분, freshness·coverage, 핵심 민감도 변수, 실행 가능성과 제외 사유, 신뢰도·불확실성 범위, 권고 결정기한과 기한 초과 시 예상 영향.
- 단일안뿐 아니라 대응 "조합"(복합 대응)의 순위화도 다룬다 — 후보를 하나씩 비교하는 것이 아니라 조합 최적화까지 책임진다.
- `후보 생성 → 제약 검증 → 시뮬레이션 → 조합 최적화` 순서를 반드시 유지한다 (`ARCHITECTURE.md` §4.4) — 시뮬레이션 결과가 없는 후보를 최적화 대상에 넣지 않는다.
- 권고 결정기한은 임의 고정값이 아니라 Impact DAG의 시각 추정(예: 안전재고 소진 예상시각)에서 역산해야 한다.

## 의존 관계

- **선행**: 시뮬레이션 에이전트(결과 취합), 제약 검증 에이전트(제외 사유)
- **후행**: 오케스트레이션 에이전트가 이 패키지를 승인 흐름에 올림
- **순차 필수**: 시뮬레이션 결과 취합 → 대응 조합 최적화 → 의사결정 패키지 → 담당자 승인 (§7.3)

## 작업 지침 (구현 체크리스트)

1. `decision_packages` 스키마에 업무 명세 §5.1의 10개 항목을 모두 필드로 강제한다 — 선택적 필드로 두면 누락이 생긴다.
2. 순위화 로직은 기대손실만이 아니라 P90/CVaR과 실행 제약(선행조건 유무)을 함께 고려하도록 구성한다.
3. 결정기한 계산은 Impact DAG의 노드별 예상 발생시각에서 역산하는 함수로 분리한다 (하드코딩된 상수 금지).
4. `GET /incidents/{id}/decision-package`는 프론트의 "근거 패널"(FACT/INFERENCE/ASSUMPTION 뱃지, 신뢰도, 결정기한 카운트다운)이 그대로 렌더링할 수 있는 구조로 응답한다.

## 완료 기준 (Definition of Done)

- [ ] 의사결정 패키지에 §5.1의 10개 항목이 모두 채워짐
- [ ] 제외된 후보의 사유가 패키지에 포함됨
- [ ] 결정기한이 DAG 시각 추정에서 역산됨
- [ ] 테스트 최소 3케이스: (1) 정상 패키지 생성 (2) 모든 후보가 제외된 극단 케이스(안전 기본안만 남는 경우) 처리 (3) 결정기한 역산 로직 검증
